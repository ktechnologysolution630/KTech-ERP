# K Tec ERP — เฟส 1: ระบบจัดซื้อ (PR → PO → รับของ → PV)

> สถานะ: ร่างแบบเพื่อขออนุมัติ · วันที่ 2026-11-02
> ป้ายกำกับ: **[ผู้ใช้]** = ผู้ใช้บอกเอง · **[ผู้ออกแบบ]** = ผู้ออกแบบตัดสินใจเอง ผู้ใช้ยังไม่ได้ยืนยัน

## 1. ทำไมต้องมี

บริษัทรับเหมาก่อสร้าง ตอนนี้ใช้ Excel ทำงานจัดซื้อ บัญชี และ Stock **[ผู้ใช้]** ปัญหาที่ผู้ออกแบบคาดไว้ (ผู้ใช้ไม่ได้แย้ง) คือไฟล์กระจายอยู่หลายที่ ไม่รู้ว่าเอกสารค้างอนุมัติที่ใคร และต้องนั่งรวมยอดเองทุกครั้ง (จ่ายแล้ว / ค้างจ่าย / ของยังไม่มา)

ผู้ใช้เลือกให้ **ระบบจัดซื้อ** เป็นเรื่องแรกที่ต้องทำให้ดี **[ผู้ใช้]**

**ถือว่าสำเร็จเมื่อ:** PR/PO/PV ทุกใบอยู่ในระบบเดียว ทุกคนเห็นว่ามีอะไรรอตัวเองอยู่ และเจ้าของตอบได้ในไม่กี่วินาทีว่า ค้างจ่ายใครเท่าไร อะไรใกล้ครบกำหนด และ PO ไหนจ่ายแล้วแต่ของยังไม่มา

## 2. ขอบเขต

### อยู่ในเฟส 1
- PR, PO (มีหรือไม่มี PR ก็ได้), การอนุมัติ
- เงื่อนไขการจ่ายใน PO 3 แบบ: เครดิต / จ่ายก่อนรับของ / จ่ายเป็นงวด
- การรับของตาม PO (รับบางส่วนได้) โดย Foreman เป็นคนยืนยัน
- การบันทึก Invoice/วางบิลจากผู้ขาย
- PV (ใบสำคัญจ่าย) สำหรับ PO, การอนุมัติ, การบันทึกว่าจ่ายแล้ว
- หน้า Dashboard / กล่องงานรออนุมัติ
- ข้อมูลหลัก: โครงการ, ผู้ขาย/ร้านค้า, รายการสินค้า/หน่วย, ผู้ใช้และบทบาท
- พิมพ์ PR / PO / PV เป็น PDF ภาษาไทย

### ไม่อยู่ในเฟส 1 (แต่ต้องออกแบบโครงข้อมูลเผื่อไว้)
ผู้ใช้เล่า workflow ทั้งหมดไว้แล้ว ส่วนต่อไปนี้จะทำในเฟสถัดไป **[ผู้ออกแบบ]**:
1. Stock หน้างานเต็มรูปแบบ (เบิก / โอน / ตรวจนับ / ขอปรับยอด พร้อมคนอนุมัติ)
2. ผู้รับเหมา (สัญญา, Advance และการหักคืน, Retention, หัก ณ ที่จ่าย, เงินทดรอง, การเบิกผลงาน)
3. ค่าแรงรายวัน (ตัดยอดวันจันทร์ จ่ายวันพุธ จ่ายนอกรอบได้)
4. ค่าใช้จ่ายที่ไม่มี PO และเงินสดย่อย
5. รายรับโครงการ (งวดงาน, Invoice ผ่านบัญชี Outsource, รับเงิน, Retention และ Bank Guarantee ฝั่งเจ้าของงาน)
6. BOQ / TOR (คุมงบตาม BOQ)

**เผื่อไว้แปลว่า:** ตาราง PV ต้องรองรับแหล่งที่มาหลายแบบในอนาคต (PO, งวดผู้รับเหมา, ค่าแรง, ค่าใช้จ่ายทั่วไป) และตารางรับของต้องต่อเข้า stock ledger ได้ในภายหลัง

### ไม่ใช่เป้าหมาย
- ระบบบัญชีเต็มรูปแบบ (ผังบัญชี, งบการเงิน): บัญชีอยู่กับ Outsource **[ผู้ใช้]**
- ยื่นภาษีออนไลน์ หรือเชื่อมต่อธนาคารโดยตรง
- แอพมือถือแบบ native (ใช้เว็บ responsive แทน)

### ถือว่าล้มเหลว แม้ระบบจะทำงานได้
- Foreman ใช้บนมือถือที่หน้างานยาก จนกลับไปจดกระดาษ
- ขั้นตอนอนุมัติแข็งเกินไป จนต้องหาทางเลี่ยงระบบ
- ยอดเงินคลาดเคลื่อน เช่น ปัดเศษผิด หรือจ่ายเกินยอด PO โดยไม่มีอะไรเตือน

## 3. ผู้ใช้และบทบาท

ประมาณ 10 คน **[ผู้ใช้]** คนเดียวมีได้หลายบทบาท **[ผู้ออกแบบ]**

| บทบาท | ทำอะไรได้ในเฟส 1 |
|---|---|
| Foreman / วิศวกร | เปิด PR ของโครงการที่ตัวเองอยู่, ยืนยันรับของ |
| PM | ทุกอย่างที่ Foreman ทำได้ + อนุมัติหรือตีกลับ PR ในโครงการของตัวเอง |
| จัดซื้อ | เปิดและแก้ PO, ส่ง PO ขออนุมัติ, บันทึกว่าสั่งของแล้ว, ดูแลข้อมูลผู้ขายและสินค้า |
| หัวหน้าจัดซื้อ | ทุกอย่างที่จัดซื้อทำได้ + อนุมัติ PO ที่ยอดต่ำกว่าวงเงินที่ตั้งไว้ **[ผู้ใช้]** |
| การเงิน | บันทึก Invoice, ทำคำขอเบิกและ PV, บันทึกการจ่าย |
| เจ้าของ (Owner) | อนุมัติ PO และ PV, ดูทุกอย่าง |
| Admin | จัดการผู้ใช้ บทบาท และโครงการ (ผู้ใช้คนแรกเป็น Admin + Owner) |

ผู้ใช้ผูกกับโครงการได้หลายโครงการ ฝั่งหน้างาน (Foreman/PM) เห็นเฉพาะโครงการของตัวเอง ส่วนจัดซื้อ การเงิน และเจ้าของเห็นทุกโครงการ **[ผู้ออกแบบ]**

## 4. Workflow

### 4.1 PR (ใบขอซื้อ)
```
Draft → Submitted → Approved (โดย PM) | Rejected → (แก้แล้วส่งใหม่ได้)
                     ↓
              Partially Ordered → Fully Ordered | Closed (ปิดเอง)
```
- PR ผูกกับโครงการเดียว มีหลายรายการ: สินค้า (เลือกจาก master หรือพิมพ์เองได้), จำนวน, หน่วย, วันที่ต้องการ, หมายเหตุ, แนบรูปได้
- ไม่บังคับใส่ราคาใน PR (ใส่ประมาณการได้) **[ผู้ออกแบบ]**
- ถ้าผู้เปิด PR เป็น PM ของโครงการนั้นเอง ยังต้องกดอนุมัติเอง (ขั้นตอนเหมือนเดิม) **[ผู้ออกแบบ]**

### 4.2 PO (ใบสั่งซื้อ)
```
Draft → Pending Approval → Approved (โดย Owner) | Rejected
          ↓
       Ordered (จัดซื้อสั่งแล้ว) → … → Completed (รับครบ + จ่ายครบ) | Cancelled
```
- เปิดจากรายการใน PR ที่อนุมัติแล้ว หรือเปิดใหม่โดยไม่มี PR **[ผู้ใช้]**
- PR หนึ่งใบแยกเป็นหลาย PO ได้ (แยกตามร้าน) และ PO หนึ่งใบดึงรายการจากหลาย PR ในโครงการเดียวกันได้ **[ผู้ออกแบบ]** ระบบเก็บว่าแต่ละรายการสั่งไปแล้วเท่าไร
- PO ไม่มี PR ต้องระบุ "โครงการ" หรือ "สำนักงาน/ส่วนกลาง" **[ผู้ออกแบบ]**
- ผู้ขาย 1 รายต่อ PO หนึ่งใบ, รายการมี ราคาต่อหน่วย / ส่วนลด / VAT 7% (ราคารวมหรือไม่รวม VAT) / ค่าขนส่ง
- **เงื่อนไขการจ่าย** (เลือก 1 แบบต่อ PO):
  - `CREDIT`: เครดิต N วัน
  - `PREPAID`: จ่ายก่อนรับของ (เต็มจำนวน)
  - `INSTALLMENT`: แบ่งเป็นงวด แต่ละงวดมี ชื่อ, % หรือจำนวนเงิน, เงื่อนไข (`ก่อนผลิต` / `ก่อนส่ง` / `หลังรับของ` / อื่นๆ ข้อความอิสระ) รวมทุกงวดต้องเท่ากับ 100% ของยอด PO
- **แก้ PO หลังอนุมัติ:** ต้องกลับไปขออนุมัติใหม่ ระบบเก็บประวัติการแก้ไข (revision) ไว้ **[ผู้ออกแบบ]**

### 4.3 รับของ (Goods Receipt)
- Foreman (หรือ PM) ของโครงการนั้นเป็นคนยืนยันรับอย่างเป็นทางการ **[ผู้ใช้]**
- รับบางส่วนได้ และรับหลายครั้งได้ **[ผู้ใช้]** แต่ละครั้งบันทึก วันที่, จำนวนที่รับในแต่ละรายการ, เลขใบส่งของ, รูปถ่าย (ไม่บังคับ), หมายเหตุ
- ห้ามรับเกินจำนวนที่สั่ง **[ผู้ออกแบบ]** (ถ้าเกินต้องให้จัดซื้อแก้ PO ก่อน)
- PO สำนักงาน/ส่วนกลาง: จัดซื้อหรือ Admin เป็นคนยืนยันรับได้ **[ผู้ออกแบบ]**
- ในเฟสนี้ การรับของยังไม่เข้า Stock แต่ต้องออกแบบให้ต่อเข้า stock ledger ได้ในเฟส 2

### 4.4 Invoice / วางบิล
- การเงินบันทึก Invoice ของผู้ขาย: เลขที่, วันที่, ยอดก่อน VAT / VAT / ยอดรวม, วันครบกำหนดชำระ (คำนวณจาก credit term ให้ก่อน แล้วแก้เองได้), แนบไฟล์
- ผูกกับ PO เท่านั้นในเฟสนี้ (Invoice หนึ่งใบผูกกับ PO เดียว) **[ผู้ออกแบบ]**
- ระบบเตือนเมื่อยอด Invoice สะสมเกินยอด PO

### 4.5 PV (ใบสำคัญจ่าย)
```
Draft (การเงิน) → Pending Approval → Approved (Owner) | Rejected → Paid (การเงินบันทึกการจ่าย)
```
- **ที่มาของ PV ในเฟส 1:** Invoice ของ PO เครดิต, คำขอเบิกของ PO จ่ายก่อน, งวดของ PO แบบแบ่งงวด
- PV หนึ่งใบจ่ายผู้ขายรายเดียว แต่รวมหลาย Invoice / งวด ได้ **[ผู้ออกแบบ]**
- ในแต่ละบรรทัดมี ยอดก่อน VAT, VAT, **หัก ณ ที่จ่าย** (เลือกอัตรา 0/1/2/3/5% คิดจากยอดก่อน VAT) และยอดจ่ายสุทธิ
- บันทึกการจ่าย: วันที่จ่าย, วิธีจ่าย (โอน/เช็ค/เงินสด), บัญชีที่จ่ายออก, เลขอ้างอิง, แนบสลิป
- **"เจ้าของอนุมัติและจ่าย"** (กรณีจ่ายก่อน) **[ผู้ใช้]**: เฟสนี้แยกเป็น 2 ขั้นคือ Owner อนุมัติ แล้วใครคนใดคนหนึ่ง (Owner หรือการเงิน) บันทึกว่าจ่ายแล้ว **[ผู้ออกแบบ]**
- **คำขอเบิก (กรณีจ่ายก่อน):** จัดซื้อกด "ขอเบิก" จาก PO ที่อนุมัติแล้ว แล้วระบบส่งเข้าคิวการเงินให้ทำ PV **[ผู้ออกแบบ]** เรื่องนี้เป็นแค่สถานะ/คิวงาน ไม่ต้องมีเอกสารแยก

### 4.6 สถานะที่ PO ต้องแสดง (สรุปจากการรับของและการจ่าย)
ทุก PO แสดงตัวเลขเหล่านี้:
- ยอด PO / ยอดรับของแล้ว (คิดตามมูลค่า) / ยอดตั้งหนี้ (Invoice) / ยอด PV อนุมัติแล้ว / ยอดจ่ายแล้ว / ยอดคงเหลือ
- ป้ายสถานะ: `รอรับของ`, `รับบางส่วน`, `รับครบ` × `ยังไม่จ่าย`, `จ่ายบางส่วน`, `จ่ายครบ`
- ป้ายพิเศษ **"จ่ายแล้ว ของยังไม่มา"** เมื่อยอดจ่าย > มูลค่าของที่รับแล้ว **[ผู้ใช้]**
- PO แบบงวด: แสดงตารางงวด (สถานะแต่ละงวด: ยังไม่ถึง / ขอเบิกแล้ว / PV / จ่ายแล้ว) + % ที่รับของแล้ว **[ผู้ใช้]**

### 4.7 ใบกำกับภาษีกับ PO จ่ายก่อนและ PO แบบงวด **[ผู้ออกแบบ]**
- PV ของ PO จ่ายก่อนหรือแบบงวด สร้างจาก "ยอดที่ต้องจ่าย" (PO หรืองวดนั้น) ได้เลย โดยไม่ต้องรอ Invoice VAT และ WHT คิดจากเงื่อนไขของ PO
- ใบกำกับภาษีที่มาทีหลัง ให้บันทึกเป็น Invoice แล้ว **จับคู่กับการจ่ายที่ทำไปแล้ว** ระบบจะไม่นับเป็นหนี้ซ้ำ ใบกำกับหนึ่งใบจับคู่ได้หลายงวด และงวดหนึ่งก็มีหลายใบได้
- ทุก PO แสดงป้าย "ยังไม่ได้ใบกำกับภาษี" ถ้ายอดจ่ายมากกว่ายอดใบกำกับที่รับแล้ว
- โครงสร้างข้อมูล: บรรทัด PV ชี้ไปที่ "รายการตั้งจ่าย" (payable) ซึ่งที่มาเป็น Invoice เครดิต, คำขอเบิกของ PO จ่ายก่อน หรืองวดก็ได้ ส่วนการจับคู่ Invoice กับ payable แยกไว้อีกตารางหนึ่ง

### 4.8 นิยามยอดเงิน **[ผู้ออกแบบ]**
- ยอดทุกตัวที่ใช้ตรวจสอบและแสดงสถานะ (ยอด PO, มูลค่ารับของ, ยอดตั้งหนี้, ยอดจ่าย) ใช้ **ยอดรวม VAT ก่อนหัก ณ ที่จ่าย** ภาษีหัก ณ ที่จ่ายถือว่าจ่ายแล้ว เพราะจ่ายแทนผู้ขายให้สรรพากร
- มูลค่ารับของ = จำนวนที่รับ × ราคาต่อหน่วยสุทธิของรายการนั้น ส่วนลดท้ายบิลและค่าขนส่งเฉลี่ยลงแต่ละรายการตามมูลค่า แล้วบวก VAT
- PO แบบงวดที่จ่ายมัดจำก่อนผลิต จะขึ้นป้าย "จ่ายแล้ว ของยังไม่มา" ตลอดช่วงผลิต ถือว่าตั้งใจให้เป็นแบบนี้ เพราะผู้ใช้อยากรู้ยอดนี้

### 4.9 ปิด PO ที่ส่งของไม่ครบ **[ผู้ออกแบบ]**
- จัดซื้อกด "ปิดยอดค้างรับ" พร้อมใส่เหตุผล แล้ว Owner อนุมัติ
- ยอด PO จะลดเหลือเท่ามูลค่าที่รับจริง เพดานห้ามจ่ายเกินลดตามไปด้วย และงวดที่ยังไม่จ่ายจะถูกปรับหรือยกเลิก
- ถ้าจ่ายไปเกินมูลค่าที่รับ ระบบขึ้น "ยอดรอคืนจากผู้ขาย" ไว้ให้ติดตาม
- จำนวนในรายการ PR ที่ยังไม่ได้รับ กลับไปเปิดสั่งใหม่ได้

### 4.10 แก้ PO ที่รับของหรือจ่ายไปแล้ว **[ผู้ออกแบบ]**
- ระหว่างรออนุมัติฉบับแก้ไข การรับของและการจ่ายยังทำต่อได้ตาม **ฉบับที่อนุมัติล่าสุด**
- ฉบับแก้ไขจะลดจำนวนหรือยอดเงิน ให้ต่ำกว่าที่รับหรือจ่ายไปแล้วไม่ได้
- รายการรับของและ PV บันทึกเลข revision ของ PO ที่ใช้ตอนนั้นไว้ด้วย

## 5. หน้าจอหลัก

1. **กล่องงานของฉัน**: เอกสารที่รอฉันจัดการ แยกตามประเภท (หน้าแรกของทุกคน)
2. **Dashboard เจ้าของ**: ยอดค้างจ่ายแยกผู้ขาย, รายการครบกำหนดใน 7 วัน / เลยกำหนด, PO ที่จ่ายแล้วแต่ของยังไม่มา, PO/PV ที่รออนุมัติ, ยอดซื้อแยกโครงการ
3. รายการ + ฟอร์ม PR / PO / Invoice / PV (ค้นหาและกรองตามโครงการ / ผู้ขาย / สถานะ / ช่วงวันที่)
4. **หน้ารับของสำหรับมือถือ** (Foreman): เห็นรายการ PO ที่รอรับในโครงการตัวเอง → แตะ → กรอกจำนวน → ถ่ายรูป → ยืนยัน ปุ่มใหญ่ ทำจบได้ในไม่กี่แตะ
5. ข้อมูลหลัก: โครงการ, ผู้ขาย (ชื่อ, เลขผู้เสียภาษี, ที่อยู่, บัญชีธนาคาร, credit term ปกติ), สินค้า/หน่วย, ผู้ใช้
6. ทุกเอกสารมีประวัติ (ใครทำอะไร เมื่อไร) + ช่องคอมเมนต์ + ไฟล์แนบ

## 6. กติกาที่สำคัญ

- **เลขเอกสาร:** `PR-YYMM-####`, `PO-YYMM-####`, `PV-YYMM-####` รันต่อเนื่องทั้งบริษัท YY เป็นปี พ.ศ. 2 หลัก และ #### เริ่มนับใหม่ทุกเดือน **[ผู้ออกแบบ]** (ปรับรูปแบบได้ภายหลัง)
- **เงิน:** เก็บเป็น decimal (ห้ามใช้ float) ทศนิยม 2 ตำแหน่ง ปัดเศษ VAT และ WHT ทีละบรรทัดแบบ half-up **[ผู้ออกแบบ]**
- **ห้ามจ่ายเกิน:** ยอด PV ที่อนุมัติแล้วรวมกันต้องไม่เกินยอด PO (Owner เท่านั้นที่ override ได้ และต้องใส่เหตุผล)
- **การอนุมัติ PO:** ตั้งวงเงินได้ในหน้า Settings PO ที่ยอดรวม VAT **ต่ำกว่าวงเงิน** ให้ **หัวหน้าจัดซื้อ** อนุมัติ ถ้าเท่าหรือเกินวงเงินต้องให้ Owner อนุมัติ **[ผู้ใช้]** Owner อนุมัติได้ทุกยอด และคนเปิด PO อนุมัติ PO ของตัวเองไม่ได้ ยกเว้น Owner **[ผู้ออกแบบ]**
- **การอนุมัติ PV และการปิดยอดค้างรับ:** ยังต้องให้ Owner อนุมัติทุกใบ **[ผู้ออกแบบ]** (เพิ่มวงเงินแบบเดียวกันได้ภายหลัง)
- **ตีกลับ:** ต้องใส่เหตุผลทุกครั้ง เอกสารกลับไปเป็น Draft ให้ผู้เปิดแก้แล้วส่งใหม่
- **ยกเลิก:** ยกเลิก PO ไม่ได้ถ้ามีการรับของหรือการจ่ายแล้ว
- **ไม่ลบเอกสารจริง** ใช้การยกเลิก (void) และเก็บ audit log ไว้

## 7. แจ้งเตือน

## 8. เอกสาร PDF
- PR, PO, PV เป็นภาษาไทย ฟอนต์ Sarabun มีโลโก้และข้อมูลบริษัท (ตั้งค่าได้ในหน้า Settings) ช่องลงชื่อผู้จัดทำ / ผู้ตรวจ / ผู้อนุมัติ
- ใช้แบบฟอร์มมาตรฐานไปก่อน **[ผู้ออกแบบ]** ถ้าผู้ใช้ส่งแบบฟอร์มเดิมมา จะปรับให้ตรงภายหลัง

## 8.1 สิ่งที่ส่งให้บัญชี Outsource **[ผู้ออกแบบ]**
- พิมพ์ **หนังสือรับรองหัก ณ ที่จ่าย (50 ทวิ)** จาก PV ที่จ่ายแล้วได้ มีเลขที่รันของตัวเอง และแบบ ภ.ง.ด.3 (บุคคล) หรือ 53 (นิติบุคคล) เลือกตามประเภทผู้ขาย
- **Export Excel รายเดือน**: รายการ PV ที่จ่ายแล้ว, ใบกำกับภาษีซื้อ (สำหรับรายงานภาษีซื้อ), รายการหัก ณ ที่จ่ายแยก ภ.ง.ด.3/53
- ข้อมูลผู้ขายต้องเพิ่ม: ประเภท (บุคคล/นิติบุคคล), เลขผู้เสียภาษี 13 หลัก, สาขา (สำนักงานใหญ่/เลขสาขา)

## 9. ข้อมูลเดิมจาก Excel
- เฟส 1 มีหน้า import ผู้ขายและสินค้าจาก CSV/Excel **[ผู้ออกแบบ]**
- PO ที่ยังเปิดค้างอยู่ ให้คีย์เข้าระบบเองตอนเริ่มใช้งาน (ไม่ทำ import เอกสารย้อนหลัง)

## 10. เทคนิค (ผู้ออกแบบเลือก ผู้ใช้ตกลงแล้ว)
- **Next.js (App Router) + TypeScript**, Tailwind CSS, UI ภาษาไทย, responsive ใช้ได้ทั้งคอมและมือถือ
- **PostgreSQL** (Neon ผ่าน Vercel Marketplace) + ORM (Prisma หรือ Drizzle ให้ผู้สร้างเลือก)
- Deploy บน **Vercel**
- ล็อกอินด้วยอีเมล + รหัสผ่าน (Admin สร้างบัญชีให้ ไม่มีสมัครเอง) **[ผู้ออกแบบ]**
- เก็บไฟล์แนบใน Vercel Blob
- **ไม่รองรับออฟไลน์ในเฟส 1** **[ผู้ออกแบบ]** ถือว่าที่หน้างานส่วนใหญ่มีสัญญาณ หน้ารับของต้องเบา โหลดเร็ว และย่อรูปก่อนอัปโหลด
- เขตเวลา Asia/Bangkok, วันที่แสดงเป็น พ.ศ. ในหน้าจอและ PDF **[ผู้ออกแบบ]**
